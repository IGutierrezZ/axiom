# OpenSpec adoption: migrating pre-existing requirements

Read this reference when `openspec/changes/{change-name}/adoption-inventory.yaml` exists. That file is the deterministic trigger: the change is an **adoption change**, an ordinary SDD change (kickoff, gates, archive) whose spec phase migrates a project's pre-existing requirement documents, in any format, into `openspec/specs/`. OpenSpec is the only living-spec format.

## Who checks what

- Go (`axiom archive adopt scan` and `axiom archive adopt check`) verifies form and coverage: format against the project's identifier pattern, unique identifiers, that the client's identifier is kept, scenarios, resolvable `Origen:` lines, and that every inventory unit is migrated or discarded with a reason.
- A human approves, at the `spec` gate, that the migration is **faithful** to its sources. No command judges semantic fidelity: a requirement can pass every check and still misstate its source. `adopt check` never records or replaces a gate decision.

## Flow

1. **Inventory.** From the workspace root of the specs repository, run `axiom archive adopt scan --path "<workspaceRoot>" --change "{change-name}"`. It is a guarded writer: it writes only `adoption-inventory.yaml` in the change folder, and outside the change branch it refuses with `wrong_branch` and the `axiom branch ensure` continuation (execute that continuation, then repeat). Without `--change` it only reports and writes nothing. Read the inventory: each source with its `path`, each unit with its `anchor`, its title and the foreign identifiers (for example `RF-120`) found in it, the `context_candidates` it proposes and, when the sources carry identifiers, the `proposed_id_pattern`. If it lists no sources, report that there is nothing to migrate.
1b. **Declare the identifier pattern.** Review `proposed_id_pattern`: its `template` (for example `RF-<NNN>`), its evidence and its conflicts. The scanner never writes `axiom.yaml`: the person copies the proposed `sdd:` / `id_pattern:` lines into `axiom.yaml` in the repository where the adoption works (the change branch, or the integration branch of the specs repository in a `multirepo`) and runs `adopt check` again. With a conflict (mixed prefixes, separators or domains) there is no template: normalize the identifiers of the source by hand, because Axiom never rewrites them, and scan again. A source without identifiers needs no declaration: the default pattern applies and the requirements use provisionals. Declaring the client's pattern is a project decision, not only an adoption one: when `openspec/specs/` already holds living specs of another scheme (for example `REQ-n.m`), those requirements stop being indexed under the new pattern, so decide it for the whole project before declaring it.
2. **Read every unit.** Open each source and read each unit before writing: the inventory is the coverage reference, not the content.
3. **Write one delta per capability** at `openspec/changes/{change-name}/specs/<capability>/spec.md`. For an adoption change the capability file is a delta with **only `## ADDED Requirements`** (never MODIFIED, REMOVED or RENAMED), even for a new capability: this takes precedence over the full-spec shape that Step 2 describes for new capabilities. Each requirement carries:
   - A title `### Requirement: <name> (<ID>)` where `<ID>` is either the client's identifier of the unit it migrates, kept as is and matching the `<original ID>` of its `Origen:` line (`RF-120` stays `RF-120`), or a provisional `prov:<series>:<ordinal>` that the archive numbers. With a fixed-series pattern such as `RF-<NNN>` the series is empty, so the provisional is `prov::<ordinal>` (for example `prov::1`). A unit without an identifier, or a requirement that merges several units, uses a provisional; one requirement per unit keeps its identifier. Never invent an identifier the source does not carry.
   - A normative statement (RFC 2119 keywords) in the artifact language of the project.
   - At least one line `Origen: <path>#<anchor> (<original ID>)`, one line per source unit it migrates (several lines are allowed). `<path>` is relative to the workspace root, with `/`; put it between backticks if it contains spaces; `<anchor>` is copied from the inventory; omit `#<anchor>` only for a whole-file unit; `(<original ID>)` is the single foreign identifier of the unit when it has one (the scanner only recognizes the prefixes `RF`, `RNF`, `RN`, `REQ`, `US`, `HU`, `UC`, `CU`, `FR` and `NFR`: with another prefix, declare the pattern by hand and write the identifier in `Origen:`). The archive keeps these lines verbatim in the living spec.
   - At least one `#### Scenario:` with verifiable GIVEN/WHEN/THEN steps, in the artifact language of the project.
4. **Discard with a reason.** Create `openspec/changes/{change-name}/adoption.md` with a `## Descartado` section: one bullet `- <path>#<anchor>: <reason>` per inventory unit that you do not migrate (a whole-file unit is `- <path>: <reason>`). The reason is never empty. Do not discard to silence a coverage failure: discard only what is not a requirement (a title, a glossary, an introduction).
5. **Check.** Run `axiom archive adopt check --path "<workspaceRoot>" --change "{change-name}"`. It reports every failure, not only the first, each with the rule (`format`, `uniqueness`, `scenarios`, `origin`, `origin_id`, `coverage`, `discard_reason`, `inventory_missing`, `inventory_stale`, `pattern_undeclared`, `foreign_id_conflict`) and the requirement, unit or project setting involved. `pattern_undeclared` means the client's identifiers do not fit the effective pattern: declare `sdd.id_pattern` as step 1b says. `foreign_id_conflict` means a unit carries several identifiers or two units share one: normalize the source or discard the unit. Fix them all and repeat until it exits `0`. On `inventory_stale` a source changed after the scan: repeat step 1 and re-evaluate coverage against the new units.
6. **Gate.** Present the migration at the `spec` gate for human approval of its fidelity. Do not claim that `adopt check` verified fidelity, and do not record the gate yourself.
7. **Archive.** The adoption change is archived like any other: `sdd-archive` integrates it with `axiom sdd archive-integrate`. The living spec keeps each client identifier, and keeps each `Origen:` line byte for byte; and a provisional receives the next number after the highest identifier of its series, definitive identifiers first.

## Limits

- Never edit the source documents.
- Never invent a requirement without an `Origen:`; never migrate Axiom's own `REQ-x.y` identifiers as if they were a client's.
- Never write `technical_context:` into `axiom.yaml` on your own: present the `context_candidates` (`maintained` or `reference`) to the user as a proposal. The same holds for `sdd.id_pattern`: the scanner proposes, the person declares.
- In a `multirepo`, the commands operate on the specs repository: its `docs/` is inventoried, the change lives in its `openspec/changes/` on the integration branch of that repository, and sources in sibling code repositories are out of the inventory.
